# SCOPE — 项目范围

## 定位

**ThreeJsRoomEditor** 是一个浏览器端、AI 原生的房间关卡编辑器，服务于一款
**多房间串联**的游戏。房间形态是**很高的仓库 / loft**：外壳为全封闭立方体、
带固定数量的门，内部靠夹层平台与室内楼梯组织竖向空间。

运行时目标是 **UE 5.8.1**。本编辑器不是运行时，是**授权与生成工具**。

## 为什么不用 UE 编辑器

1. **太重** —— 摆几个盒子房间不需要开一个完整的 DCC
2. **对 LLM 不友好** —— `.umap` 是二进制，AI 无法读写，diff 无意义

本项目的存在理由就是这两条。任何让编辑器变重、或让数据变得不可被 LLM 读写的
改动，都在违背项目前提。

## 五条设计原则

### P1. 文档即真相

关卡是一份小而语义化的 YAML。存**意图**，不存推导结果（房间世界坐标由 solver
计算，**绝不写入文档**）。

**硬指标：30 房间的关卡 < 1500 行、< 20k tokens，可整份进 LLM 上下文。**

### P2. 图驱动布局

房间世界坐标由**连接关系自动求解**，作者只描述拓扑。

理由很实际：**LLM 做空间坐标算术很差，做拓扑关系很好。** 让 solver 承担几何，
让 LLM 承担语义。

### P3. 单一命令层

UI、AI agent、CLI、测试全部通过同一套 typed command 修改文档。禁止任何地方直接
mutate。免费获得 undo/redo、回放、确定性、审计日志，以及**人与 AI 能力对等**。

### P4. AI 输出命令，不输出代码

外部 agent 产出的是文档编辑或命令 JSON，经 schema 校验后应用。
**永不执行 LLM 生成的任意代码。**

### P5. 约束优先

材质 / 主题 / 道具 / 灯光全部走白名单预设库，不允许自由 shader。
**源头能表达的必须落在 UE 侧能自动重建的范围内**，否则导出必然失真。

## v1 范围内

### 房间模型

| 概念         | 说明                                                                                                                                          |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `Room`       | 轴对齐立方体外壳，**全封闭**，内部净尺寸 `{w,d,h}`                                                                                            |
| `doorCount`  | 声明式门数约束，校验器核对                                                                                                                    |
| `Opening`    | `door` / `window` / `arch` / `passage` / `hidden`，带 `offset` + `size` + `elevation`                                                         |
| `Structure`  | 内部结构件，**带碰撞与导航语义**：`platform`（= 夹层）/ `stair` / `ladder` / `ramp` / `catwalk` / `railing` / `pillar` / `beam` / `partition` |
| `Prop`       | 预设库道具实例（无导航语义）                                                                                                                  |
| `Light`      | 预设驱动光源：`point` / `spot` / `area` / `ambient`                                                                                           |
| `Marker`     | gameplay 标记：`spawn` / `trigger` / `objective` / `nav_hint` / `cover` / `item`                                                              |
| `Theme`      | 材质 + 灯光预设集合                                                                                                                           |
| `Connection` | opening ↔ opening，带 `locked` / `keyId` / `oneWay` / `transition`                                                                            |

### 布局求解

- 从连接图求解世界坐标（轴对齐 + 90° 倍数旋转）
- 冲突检测：房间重叠、开口不对齐、悬空连接、**不可达房间**
- 手动 `pin` 锚定

### 编辑器

- 3D 视口（`WebGPURenderer`，自动 WebGL2 回退）：orbit / fly、gizmo、grid snap
- **2D 拓扑图视图**（串联游戏最高效的编辑视图）
- Inspector：**schema 驱动自动生成**
- **文本模式**：直接编辑 YAML，与 3D 双向实时同步
- **write-through + file watcher 热重载**：外部 agent 改文件，浏览器立即更新
- 校验面板、undo/redo
- **第一人称漫游预览**（验证尺度感与串联流程）

### 导出

- 原生 `.roomgraph.yaml`
- glTF 场景
- UE 5.8.1 导入包（Phase 5）

## v1 明确不做

> 每次 PR review 对照本清单，防止蔓延成"再造一个更差的 UE 编辑器"。

- ❌ 非盒体房间（L 形、曲面、斜屋顶、地形）
- ❌ **多楼层关卡拓扑**（房间图保持单层平面；房间**内部**的竖向结构是支持的）
- ❌ 任意角度旋转、非 90° 连接
- ❌ 自由 shader / 材质图编辑
- ❌ 骨骼动画、角色、AI 行为
- ❌ 光照烘焙（Phase 5 交给 UE GPU Lightmass）
- ❌ 多人协同编辑
- ❌ UE → 编辑器 反向回写
- ❌ 完整 gameplay 模拟

## 性能目标

v1 以 **50 房间**流畅编辑为目标。超出后再考虑分区流式加载。
